# BYOR hosted agent — Step 1 container

Minimal Foundry hosted agent image for the "bring your own registry" (JFrog + OIDC) walkthrough.

This repository owns only the **agent**: image build, JFrog push, hosted-agent Terraform and smoke tests. The Foundry-to-JFrog registry connection, the shared CI runner, the Terraform state account and the foundation deployment identities belong to the **foundation (platform) repository** (`jfrog-oidc-foundry`). This repo consumes what the platform publishes (the *platform contract*) and never reads foundation Terraform state.

## Files

| File | Purpose |
|---|---|
| `app.py` | FastAPI app serving `POST /responses` (Responses protocol) and `GET /healthz` |
| `Dockerfile` | `linux/amd64`, python:3.12-slim, non-root uid 10001, listens on `$PORT` (8088) |
| `requirements.txt` | fastapi + uvicorn; openai + azure-identity only needed for model mode |
| `build-and-push.sh` | Build → local smoke test → push to JFrog |
| `infra/hosted-agent/` | Terraform (AzAPI data plane) for the logical hosted agent; imports the existing agent and preserves its Foundry version history |
| `scripts/test-hosted-agent.py` | Waits for one exact version to become active, verifies its image, and invokes its Responses endpoint |
| `deploy.ps1` / `deploy.sh` | Manual plan/apply of the hosted-agent stack (needs network access to the state account) |
| `.github/workflows/deploy-agent.yml` | CI/CD: build → push to JFrog → Terraform agent version → REST readiness and smoke test |
| `.github/platform-contract.env.example` | The platform-contract keys this repo consumes, plus the app-owned variables |
| `scripts/bootstrap-github-oidc.ps1` | One-time: agent Entra app + GitHub OIDC credential, RBAC, `agent-tfstate` container, protected `agent` environment, contract variables |
| `knowledge/azure-assets.md` + `scripts/generate-asset-inventory.ps1` | Generated asset inventory bundled into the agent as its knowledge base |
| `azure.yaml` | Legacy azd compatibility/reference only; not the deployment source of truth (its endpoint, image tag and connection name are stale) |

## Modes

- **Echo mode (default).** No model call. Proves Foundry exchanged the OIDC token, pulled the image from JFrog, and started the container. Use this for the first deploy — it isolates the registry plumbing from everything else.
- **Model mode.** Set `AZURE_AI_MODEL_DEPLOYMENT_NAME` (e.g. `gpt-5-mini`) in the agent's `env` map in `azure.yaml`. The agent calls the Responses API on the Foundry project endpoint (`FOUNDRY_PROJECT_ENDPOINT`, injected by the platform) with its own Entra identity. The image holds no keys, and you don't need to assign roles because the platform-managed agent identity (which can change between deployments) can reach project models by default. For local runs, also set `FOUNDRY_PROJECT_ENDPOINT`.
- **Knowledge base.** Every `knowledge/*.md` file is copied into the image and added to the model instructions, so the agent can answer questions about this project's assets. `knowledge/azure-assets.md` is generated by `scripts/generate-asset-inventory.ps1` from live Azure, Entra and GitHub data (platform facts come from the `agent` environment variables). IDs are redacted and no secrets are read. To refresh: run the script, commit, push; the pipeline redeploys because `knowledge/**` is a trigger path. The files are sent in full with every request, which suits a few small files; above about 60 KB, switch to a Foundry vector store with `file_search`.

## Run it

```bash
export JFROG_HOST="yourtrial.jfrog.io"
export JFROG_REPO="byor-demo-docker"   # same value as the platform contract's JFROG_REPO
export IMAGE_TAG="0.1"

docker login "$JFROG_HOST"
./build-and-push.sh
```

Local check, if you want it by hand:

```bash
docker run --rm -p 8088:8088 "$JFROG_HOST/$JFROG_REPO/agent:0.1"
curl localhost:8088/healthz
curl -X POST localhost:8088/responses -H 'Content-Type: application/json' \
  -d '{"input":"Respond with a short deployment confirmation."}'
```

Expected: a JSON envelope with `status: "completed"` and an `output_text` field.

## Platform contract (what the foundation repo provides)

The foundation repo publishes a non-secret contract per environment: `foundry-<env>.json` in the `platform-contract-<env>` workflow artifact. It holds a flat `values` map and a `valuesSha256` over it. This repo consumes these keys unchanged:

| Key | Used for |
|---|---|
| `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `AZURE_RESOURCE_GROUP` | Azure login and scope |
| `FOUNDRY_ACCOUNT_NAME`, `FOUNDRY_PROJECT_NAME`, `FOUNDRY_PROJECT_RESOURCE_ID` | Project identification; the connection ID is derived from the resource ID |
| `FOUNDRY_PROJECT_ENDPOINT` | Hosted-agent data-plane endpoint |
| `JFROG_REGISTRY_CONNECTION_NAME` | Connection the agent references (`registry_connection_name`); validated live before Terraform runs |
| `JF_URL`, `JFROG_REPO` | Image path `<JF_URL host>/<JFROG_REPO>/agent` |
| `JFROG_GITHUB_OIDC_PROVIDER` | JFrog login from GitHub Actions |

The contract also carries `FOUNDRY_PROJECT_PRINCIPAL_ID`, `JFROG_REGISTRY_CONNECTION_ID`, `REGISTRY_TOKEN_AUDIENCE`, `REGISTRY_TOKEN_ENDPOINT` and `REGISTRY_OIDC_PROVIDER_NAME`; the bootstrap copies all of them, but the agent workflow does not need them. `PLATFORM_CONTRACT_VERSION` is no longer used: integrity is checked once, when the contract is copied (below).

Rules:

- Copy contract values only from the published artifact, never from foundation Terraform state or `terraform output`. The agent identity has no access to foundation state.
- The agent workflow only validates, never edits, the connection. If the live connection (target, `registry_connection` type, `oauth_token_exchange` mode) doesn't match, it fails before Terraform runs; fix it in the foundation repo.
- Variable names the contract does not carry (`agent` image name, SKU list, model deployment, state coordinates, CPU/memory) are owned here.

## Hosted-agent deployment with Terraform and AzAPI

This repository deploys the Foundry hosted agent without `azd deploy`. Terraform manages the logical hosted agent, a Foundry data-plane resource managed by `azapi_data_plane_resource` with type `Microsoft.Foundry/agents@v1`. The registry connection it references is created and owned by the foundation repo.

Changing the configured image creates a version under the existing `private-registry-agent`; it doesn't replace the logical agent. The existing `@latest` endpoint selector makes the newest active version the default while older versions remain in Foundry history.

### Important files and assets

| File or asset | Purpose |
|---|---|
| `infra/hosted-agent/` | Imports and manages `private-registry-agent`, its container definition, environment, protocol, and candidate versions. |
| `infra/hosted-agent/main.tf` | Contains the data-plane import ID, agent definition, and `prevent_destroy` protection. |
| `infra/hosted-agent/terraform.tfvars.example` | Documents the project endpoint, digest image, connection, and model inputs. |
| `private-registry-agent` | Existing logical Foundry agent. Terraform imports it instead of recreating it. |
| `jfrog-registry` | Foundation-owned Foundry project connection through which Foundry obtains a short-lived JFrog pull token (referenced via `JFROG_REGISTRY_CONNECTION_NAME`). |

State lives in a dedicated container in the platform-owned state account:

```text
agent-tfstate/hosted-agent/<environment>.tfstate      (this repo)
foundation-tfstate/registry-connection/<environment>.tfstate   (foundation repo; not accessible here)
```

The agent identity receives `Storage Blob Data Contributor` only on `agent-tfstate`, so it cannot read, lock, update, or delete foundation state. The bootstrap script fails if the identity holds a blob data role anywhere else. The account is private, so Terraform must run from a network with access to its private endpoint, normally the platform-owned self-hosted runner.

### Manual deployment

Prerequisites:

- The `linux/amd64` image has already been pushed to JFrog and you know its digest.
- Azure CLI is signed in to the correct tenant and subscription.
- Terraform 1.7 or later and AzAPI 2.13 are available.
- `infra/hosted-agent/backend.hcl` exists (written by the bootstrap script; start from `backend.hcl.example`).
- The machine can reach the private Terraform state endpoint.
- The contract file `foundry-<env>.json` is downloaded from the foundation repo's artifact (or pass `-ProjectEndpoint` and `-RegistryConnectionName`).

```powershell
.\deploy.ps1 `
  -ContractFile .\foundry-dev.json `
  -Image "trialndswdc.jfrog.io/byor-demo-docker/agent@sha256:<64-hex-digest>"
```

Review the plan when prompted, or add `-AutoApprove`. Bash equivalent (needs `jq`):

```bash
CONTRACT_FILE=./foundry-dev.json \
IMAGE="trialndswdc.jfrog.io/byor-demo-docker/agent@sha256:<64-hex-digest>" \
  ./deploy.sh
```

The image must be digest-pinned; tags are rejected. To run Terraform directly:

```bash
terraform -chdir=infra/hosted-agent init -backend-config=backend.hcl
terraform -chdir=infra/hosted-agent plan -out=tfplan
terraform -chdir=infra/hosted-agent apply tfplan
terraform -chdir=infra/hosted-agent output -raw agent_version
```

For the first hosted-agent apply, keep `import_existing_agent = true`. Terraform imports the existing logical agent into the new state before writing the requested definition. The import block is idempotent after adoption.

### Manual deployed-agent validation

After apply, acquire a Foundry data-plane token and run the same validation used by CI:

```powershell
$env:AZURE_AI_ACCESS_TOKEN = az account get-access-token `
  --resource https://ai.azure.com `
  --query accessToken `
  --output tsv

$version = terraform -chdir=infra\hosted-agent output -raw agent_version

python scripts\test-hosted-agent.py `
  --endpoint "https://<account>.services.ai.azure.com/api/projects/<project>" `
  --agent "private-registry-agent" `
  --version $version `
  --expected-image "trialndswdc.jfrog.io/byor-demo-docker/agent@sha256:<64-hex-digest>"
```

The check fails if the version enters a failed state, becomes active with a different image, times out, or doesn't return a completed Responses payload.

### Gotchas

- **Use one deployment owner.** After Terraform adopts the agent, don't use `azd deploy` or make unmanaged portal/SDK definition changes to the same agent.
- **Review the first plan carefully.** It should import and update in place with no destroy. `prevent_destroy = true` provides an additional guard.
- **Old versions are retained.** A new image creates a new version; it doesn't erase the previously active version.
- **`@latest` controls the default.** The current endpoint routes 100% to `@latest`, so a newly active version becomes the default.
- **Use immutable images.** CI pushes a commit-specific tag, resolves it to the JFrog `sha256` digest, and passes only the digest URI to Terraform.
- **Registry push and pull identities differ.** GitHub OIDC pushes the image; the Foundry project identity independently exchanges a token through the foundation-owned connection to pull it.
- **A successful apply isn't readiness.** Always wait for the exact Terraform output version and verify that its image matches the intended release.
- **Don't commit local inputs or state.** `terraform.tfvars`, `backend.hcl`, plans, `.terraform/`, and state files are ignored.
- **The runner must be online.** If the deploy job remains queued, the platform-owned `byor-private` runner is offline; start it per the foundation repo's runbook.

## CI/CD (GitHub Actions)

One workflow, `deploy-agent.yml`, supports manual dispatch, and every external login uses OIDC rather than a stored cloud or registry credential. Both jobs run in the protected `agent` GitHub Environment (`main` only; required reviewers when the GitHub plan supports them).

| Job | Runner | Steps |
|---|---|---|
| `build` | `ubuntu-latest`, `agent` environment | JFrog login with GitHub OIDC → `docker build` linux/amd64 → container smoke test → push `agent:sha-<commit>` → resolve immutable digest URI |
| `deploy` | self-hosted (`byor-private`), `agent` environment | Azure OIDC with the agent identity → validate the platform contract and live connection → import/update the Foundry data-plane agent → validate the exact candidate version |

It runs for application and `infra/hosted-agent/` changes. Manual dispatch accepts `image_tag` to redeploy an existing image without building.

### One-time setup

1. **Foundation first.** The foundation repo must have applied for your environment and published its contract (`platform-contract-<env>` artifact), the state account must exist, and a runner labelled `byor-private` must be online for this repository (platform-owned; see the foundation README). This repo must be private or internal.
2. **Run the bootstrap**, pointing at the downloaded contract:

   ```powershell
   ./scripts/bootstrap-github-oidc.ps1 -Repo <owner>/<repo> `
     -ContractFile .\foundry-dev.json `
     -StateStorageAccount <platform state account> `
     -Reviewers <user>,<org>/<team>
   ```

   On a GitHub plan that rejects required reviewers for private repos (HTTP 422 "billing plan"), pass `-NoRequiredReviewers` instead of `-Reviewers`. The `main`-only branch policy still applies, but a push to `main` then builds and deploys with no approval; re-run with `-Reviewers` once your plan supports it.

   It verifies the contract's `valuesSha256` (equivalent to `jq -S -c .values foundry-<env>.json | sha256sum`) before writing anything, then:
   - creates the agent Entra app with a federated credential for subject `repo:<owner>/<repo>:environment:agent` (ID-based subject prefixes are handled);
   - creates the `agent-tfstate` container and grants the agent identity `Storage Blob Data Contributor` on it only, `Foundry Project Manager` on the project and `Reader` on the resource group;
   - creates the `agent` environment with required reviewers (unless `-NoRequiredReviewers`) and a `main`-only branch policy, reads it back, and fails if either is missing;
   - copies the contract values and the app-owned variables (`AGENT_AZURE_CLIENT_ID`, `AGENT_STATE_RESOURCE_GROUP`, `AGENT_STATE_STORAGE_ACCOUNT`, `AGENT_STATE_CONTAINER`, `AGENT_STATE_KEY`, `MODEL_DEPLOYMENT_NAME`, `SUPPORTED_AGENT_SKUS`, optional `RAI_POLICY_ID`) into the `agent` environment, and sets repository variables `RUNNER_LABEL` and `TERRAFORM_VERSION`;
   - writes `infra/hosted-agent/backend.hcl` (git-ignored).

   Re-run it to refresh the variables when the foundation publishes a new contract. It warns about leftover repository-level variables and branch-subject federated credentials from the old single-repo setup; delete them after cutover.
3. **JFrog.** Add (or reuse) the OpenID Connect integration for GitHub named in `JFROG_GITHUB_OIDC_PROVIDER`:
   - Provider URL `https://token.actions.githubusercontent.com`.
   - Identity mapping claims `{"repository":"<owner>/<repo>","ref":"refs/heads/main"}` (the `ref` claim is still present in environment-scoped tokens), scoped to a group or user with Read + Deploy/Cache on the **local** Docker repo behind `JFROG_REPO` (`byor-demo-docker-local`). Pushes to a virtual repo land in its default deployment repo.

### Notes

- **Why a self-hosted runner:** a subscription policy forces `publicNetworkAccess=Disabled` on storage accounts, so GitHub-hosted runners can't reach Terraform state. The runner and its private endpoint are provisioned by the foundation repo, not here.
- **Independent workflows:** the agent workflow has no foundation backend variables or registry-connection steps. Container-scoped RBAC prevents its identity from accessing foundation state even if a workflow is modified.
- **Preflight:** the deploy job checks the contract variables, the project endpoint, the connection (target, type, `oauth_token_exchange` mode), the digest repository and the requested SKU before Terraform runs.
- **Agent ownership:** `infra/hosted-agent` is the deployment source of truth. The workflow resolves the release tag and passes its immutable JFrog digest URI as `TF_VAR_image_uri`.

## Caveats

- The Microsoft Learn BYOR article specifies the protocol name and version (`responses` / `2.0.0`) but not the full request/response wire contract for a self-built container. The envelope here follows the standard Responses shape (`output[].content[].output_text` plus the `output_text` convenience field) and accepts `input` as either a plain string or a message array. If Foundry's invoke returns a protocol error, capture the actual request body it sends and adjust `create_response` — the pull path is unaffected.
- Build `linux/amd64` explicitly. On Apple silicon the wrong arch pulls fine and then never reaches Active.
- Pinned dependency versions are a starting point — bump before anything customer-facing.
